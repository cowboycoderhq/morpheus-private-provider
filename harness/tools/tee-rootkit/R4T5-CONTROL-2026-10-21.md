## 1. Why the old arm was inconclusive

The root kit tried two arms against `waitclient` (pid 86687):

```
launchctl bootstrap pid/86687 .../fake/MTLCompilerService.xpc  -> Bootstrap failed: 5: Input/output error
launchctl bootstrap pid/86687 .../fake/TEEFakeCtl.xpc           -> Bootstrap failed: 5: Input/output error
```

Files: `bootstrap.txt`, `bootstrap-ctl.txt`, `piddomain.txt` in
`logs/tee-rootpass-<date>-<time>/`.

The Apple-named fake did not run. The test-named control fake did not run
either. So the run did not separate this pair:

1. launchd refuses an Apple name.
2. launchd refuses every outside bootstrap into a pid domain.

The kit comment at `tools/tee-rootpass.sh:202` already names the cause:
launchd accepts a pid-domain bootstrap only from the domain's own process.
The arm needed a control that reaches the domain by the route that launchd
does accept.

## 2. Mechanism

`com.apple.MTLCompilerService` is not a global Mach service that a client
looks up in the user domain. It is an XPC service inside Metal.framework:
`/System/Library/Frameworks/Metal.framework/Versions/A/XPCServices/MTLCompilerService.xpc`
(staged copy: `scratch/r4t5/system-copy/MTLCompilerService.xpc`). libxpc
resolves that bundle into the **caller's pid domain**. The launchd pid domain
belongs to the process that owns the bundle. An outside process can neither
add a service to that domain nor reach the service already in it.

Three measurements fix the mechanism:

1. A test-named service embedded in the app's `Contents/XPCServices` is
   launched by launchd and answers the app. Control fires.
2. `launchctl bootstrap pid/<pid>` from another process is refused, even
   when the same bundle loads in `gui/501`.
3. An app that embeds a bundle named `com.apple.MTLCompilerService` does not
   get its binary. launchd binds the name to the system bundle.

Point 3 has direct evidence. The app's entry appears in the pid domain, but
the service entry has pid 0 and status -6:

```
services = {
           0     -6     com.apple.MTLCompilerService
}
```

The matching crash report is
`~/Library/Logs/DiagnosticReports/MTLCompilerService-<date>-<time>.ips`.
The crashed process is pid 47450, parent `launchd`, signal `SIGABRT`. The
faulting frame is Apple's code, not the probe:

```
MTLCompilerService<CompilerPluginInterface>::messageHandler(NSObject<OS_xpc_object>*)
```

The probe binary has no such symbol. So launchd started the **system**
binary for the app's same-named entry. The app's fake never ran. The crash
came from the probe sending a non-compiler dictionary to the real service.
The harness does not repeat that message.

### 3.1 User-namespace registration, with a normal Metal client

An XPC service bundle can be bootstrapped into `gui/501`:

```
launchctl bootstrap gui/501 .../TEEFakeCtl.xpc   -> rc=0
launchctl print gui/501/com.tee.fakectl          -> type = XPCService, state = not running
```

A client with no bundle and a bundle-relative lookup does **not** reach it:
`outsider error: Connection invalid`. A client that uses
`xpc_connection_create_mach_service` **does** reach it:

```
OUTSIDER2 GOT REPLY service=com.tee.fakectl marker=ran
state = running, pid = 43349
```

The same holds for an ad-hoc fake under the Apple name. It loads in `gui/501`
and answers a Mach lookup:

```
launchctl bootstrap gui/501 .../svc-applefake.xpc  -> rc=0
OUTSIDER2 GOT REPLY service=com.apple.MTLCompilerService marker=ran
state = running, pid = 43948
```

But a normal Metal client ignores it. With the Apple-named fake already
running in `gui/501`, one fresh compile gives:

```
metal: library=ok pipeline=ok err=-
fake state: not running   (it was never contacted)
fake events: (none)
```

Bootout, then the baseline compiles again: `library=ok pipeline=ok err=-`.
The same result holds for a Metal probe that runs from an app which embeds
an Apple-named fake: `pipeline=ok`, no fake event.

So the user namespace accepts the fake. Metal does not consult it.

| `tools/tee-rootkit/r4t5/xpchost.m` | host with the bundle-relative lookup |

| `tools/tee-rootkit/r4t5/metalprobe.m` | normal Metal client, one fresh pipeline |
| `tools/tee-rootkit/R4T5-CONTROL-2026-10-21.out` | stored output of this run |

`svcprobe` takes the event log path at build time (`-DTEE_FAKE_LOG_PATH`).
The launchd-started service does not inherit an arbitrary environment
variable, so the path is compiled in. The log stays in the work directory.

The harness runs six cases:

| Case | What it does | PASS rule |
|---|---|---|
| C1 control-embedded-pid | app embeds a test-named service and connects | reply **and** fake event |
| C2 outsider-isolation | no-bundle Mach lookup for the C1 name | no reply |
| C3 bootstrap-pid-foreign | `launchctl bootstrap pid/<live>` | rc != 0 |
| C4 bootstrap-gui-control | same bundle in `gui/501` | rc = 0 **and** outsider reply |
| C5 apple-embedded-pid | Metal probe in an app with an Apple-named fake | `pipeline=ok` **and** 0 fake events |
| C6 gui-apple-before-metal | Apple fake live in `gui/501` before Metal starts | fake answers Mach, Metal compiles, 0 fake events during Metal |

C1 and C4 are the controls. C5 and C6 are the target cases. A target case
cannot pass without its control.

## 5. Conclusion

The per-pid namespace restriction is real and it is launchd-enforced.

1. launchd starts an embedded XPC service in the pid domain of its own
   bundle (C1).
2. No other process can add to or reach that domain (C2, C3).
3. The same bundle loads in the user domain, so the C3 refusal is specific
   to the foreign pid domain, not a broken launchd (C4).
4. `com.apple.MTLCompilerService` stays bound to the system Metal.framework
   bundle. An app-embedded same-named fake does not run (C5). The manual
   probe shows why: launchd starts the system binary for that name, and the
   crash report carries Apple's symbols.
5. A user-domain registration of an Apple-named fake does run and answer
   Mach lookups, but a normal Metal client does not contact it (C6).

Grade for the prior root arm: **INCONCLUSIVE as run**. Its control did not
fire in that run. Do not change that grade. The design above supplies the
missing control and supports the target property at the Metal-resolution
level.

Grade for the new comparison cases: **PASS**, 6 of 6, each target backed by
a control that fired.

## 6. Limits

- The harness runs as uid 501. The root case (root bootstraps into the pid
  domain of another user's process) is not re-run here, because the lane
  forbids sudo. The prior root run recorded the same rc=5. The design does
  not depend on the caller's uid: the restriction is domain ownership.
- The sealed child was not started. The result applies to it because the
  child uses the same Metal.framework resolution path. The end-to-end test
  against the live child (server start, request, fake event check) is still
  open. The engine was not running during this work.
- C6 holds the Apple-named fake in `gui/501` for a short window. It answers
  a Mach lookup from the harness. No other user process was exercised
  beyond the Metal probe. The probe is a normal, unsandboxed Metal client.
- One manual probe sent a non-Metal dictionary to the real service. That
  killed one compiler-service instance with SIGABRT. The harness does not
  send that message. Metal compiles fine before and after.
- The harness writes its build products and event log under the work
  directory. The default is `scratch/r4t5-run`. Pass `--work` to move it.
