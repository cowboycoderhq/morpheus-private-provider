# K-2: freed chunked-KV memory, cross-process read (2026-10-23)

Task: `scratch/TASK-gpu-tests.md`, test K-2 (audit `review/AUDIT-v2-1-CHILD.md` K-2, claim limit 4 in `review/CLAIM-v2-2026-10-23.md`).
Question: the chunked KV cache releases private `MTLBuffer` chunks that held prompt and reply KV data while the child runs. Can a different process (same user, unsandboxed) get those pages with the child's bytes still in them?
Host: M5, `Mac17,7`, macOS `27.2-beta`, uid 501. No `sudo`. Nothing pushed. `child/` was not restaged. `~/projects/morpheus-pnode` was not touched. The running engine was not stopped.

## Verdict

**PASS** (run 2, `neg/k2-2026-10-23.txt`, `# result: 0 failed, 0 void`; run 1 gave the same result).

The test child released 43 KV chunks (732,712,960 bytes, 698,828,804 of them nonzero) while it ran. It recorded 43,474 distinct 32-byte samples of those chunks. A separate reader process then got 16.1 GB of fresh memory with real physical backing. It found **0 child samples and 0 canary-text hits**. Every byte of that fresh memory was zero. The same-process control found 65,520 of 65,520 samples of released, uncleared memory, so the reader can find recorded bytes when they are present.

Limit: user space cannot see physical page numbers. The result shows that the pages the reader got held no child bytes, and that every fresh page held only zeros. It does not show that the reader got the exact physical pages that the child released. The reader took 22 times the released size (17.6 times in private buffers alone). Every page it got was zero-filled, so the zero-fill is not specific to the child's pages.

## Criteria (written before the build and the run)

Terms:

- **Child sample.** A 32-byte window of a released KV chunk, read by the test child just before the release. The child takes one window at in-page offset 1024 of each 16 KiB page of the chunk. It keeps only windows with 12 or more distinct byte values, so zero pages and constant fill do not count. The child writes the windows as hex, with the chunk SHA-256, to the reason file.
- **Hit.** A full 32-byte match of a sample at any 8-byte-aligned offset of memory that the reader got fresh. The reader also counts the ASCII canary text.
- **Reader.** `neg/K2/k2-reader`, a separate unsandboxed process (uid 501). It allocates fresh private `MTLBuffer` objects (chunk size, 17,039,360 bytes), copies each one to a shared buffer with a blit, and scans it. It also scans fresh shared `MTLBuffer` objects and fresh anonymous CPU pages (one byte written at the end of each page to make the kernel back the page, the other bytes only read).
- **Control.** The same reader binary and the same scan code, in control mode, in one process: a helper fills private buffers (and, in a second variant, buffers placed in a private `MTLHeap`) with random bytes, takes samples by the same rule, releases the buffers without a clear, then the reader part allocates fresh buffers and scans them.

PASS needs all of these:

1. The test child loads in the sandbox (`SANDBOXED then LOADED` path through `sealed-launch`) and answers the canary request with HTTP 200.
2. The child releases at least 8 KV chunks while it runs, and records at least 1,000 child samples in total. The release lines come before the reader starts.
3. The control fires: in at least one same-process variant, the reader finds at least 50 % of the helper's samples.
4. The reader runs after the release, while the child still runs. It scans at least 8 GiB of fresh private buffers, plus fresh shared buffers and CPU pages, and finds **0 child-sample hits and 0 canary-text hits**.
5. The production child holds no test strings: `strings -a splash/build/splash | grep -c SEALED_TEST` is 0.
6. `neg/run-all.sh` passes 95/95 after the test.

FAIL: the reader finds 1 or more child-sample hits, or 1 or more canary-text hits, in fresh memory.

VOID: the control finds 0 of its samples in every variant, or condition 1, 2 or 4 (except the hit counts) is not met, or the reader cannot scan the planned amount.

Measured, not a gate:

- A cross-process ordinary-target leg: an ordinary unsandboxed process (`k2-reader plant`) writes random bytes to private buffers of chunk size, takes samples, frees the buffers and exits. Then the reader scans in a new process. This shows whether the attack works across processes on an ordinary target.
- The nonzero byte count of fresh chunks in the child (read before the first KV write) and of the reader's fresh memory.

Known limit, stated before the run: a user process cannot see physical page numbers. A zero-hit result shows that the pages the reader got held no child bytes. It does not show that the reader got the physical pages that the child released. The reader takes many times the released size to make reuse likely.

### Change after run 1 (stricter only)

Run 1 passed. After run 1, I found one falsifier that the criteria did not cover: a fresh buffer that nobody writes can be backed lazily by one zero page, so a read of it proves nothing about reused pages. For run 2, the reader writes one byte at the end of each 16 KiB page of each private buffer (with a blit) and of each shared buffer (with the CPU) before the scan. It also prints its physical footprint growth. The driver gives VOID if the private footprint growth is less than 90 % of the private bytes scanned. The written bytes are subtracted from the nonzero count. The other criteria did not change. Run 1 is kept as `neg/K2/run/k2-run1.txt` (reader source `neg/K2/run/k2-reader-run1.m`).

## Method

### Test child (`SEALED_TEST_K2_KVDUMP`)

- `splash/runtime` is an input of the production build identity (`dev/tools/build_identity.py` hashes every runtime source). An edit there changes the production binary at the next rebuild. So the test child is built from a copy: `scratch/k2-src` (rsync of `splash/` without the `build*` folders). At copy time (<time>), `diff -rq splash/runtime scratch/k2-src/runtime` printed no difference.
- Changes in the copy only, all under `#if defined(SEALED_TEST_K2_KVDUMP)`:
  - `runtime/metal/MetalBackend.hpp`, `.mm`: `MetalBackend::copyForTest` blits a buffer into a shared buffer on a separate test queue and waits.
  - `runtime/ops/Q8PageStorage.mm`: `k2Dump` copies a chunk to one shared staging buffer, writes `test: k2 <phase> chunk=… bytes=… nonzero=… samples=… sha256=…`, and for a release one `test: k2 s chunk=… off=… <64 hex>` line for each sample. The staging buffer is set to zero after each copy and is kept to the end, so the hook makes no CPU copy of KV bytes that is later freed. The `fresh` phase runs after the chunk allocation and before `addIndirectResource`. The `release` phase runs in `releaseBackingForPage` after the `commandIdle()` check and before `removeIndirectResource`.
- Build: `cp -Rp splash/build-reason scratch/k2-src/build-k2`, then in `scratch/k2-src`:
  `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer BENCH_OK=1 nice -n 10 make -j4 BUILD=build-k2 SEALED_DEFS='-DSPLASH_SEALED -DSEALED_TEST_REASON_FILE=\"/tmp/sealed-reason.log\" -DSEALED_TEST_K2_KVDUMP'` (rc=0, `logs/build-k2-2026-10-23.log`). Binary SHA-256 `<h51>…2f979f`. Its ad hoc pin in the run was `<h52>`.

### Reader (`neg/K2/k2-reader.m`)

- Build: `clang -O2 -Wall -Wextra -fobjc-arc -framework Foundation -framework Metal neg/K2/k2-reader.m -o neg/K2/k2-reader`. Run-2 binary SHA-256 `<h53>…777fe2`.
- `scan`: loads the samples into a hash table keyed by the first 8 bytes. It checks every 8-byte-aligned offset and confirms a hit with a full 32-byte compare. It counts every nonzero byte and every `memmem` match of the canary. It keeps all buffers allocated to the end of the scan, so each new buffer gets new pages.
- `control`: three same-process variants: plain private buffers, private buffers placed in one placement `MTLHeap`, and plain shared buffers.
- `plant`: the ordinary cross-process target.

### Driver (`neg/run-k2.sh`) and leg (`neg/K2/leg.sh`, `neg/K2/req.py`)

1. `k2-reader control 1`.
2. `k2-reader plant <file> 2`, then a new process `k2-reader scan <file> … 12 1 2`.
3. `neg/CKV/with-server.sh scratch/k2-src/build-k2/splash k2-child 32768 neg/K2/leg.sh <canary> 500 12 1 2`. This is `server.py` and `launcher/sealed-launch` with the test child pinned by its own CD hash. The leg sends one request with 500 lines that each hold the canary twice, and it asks for the canary three times (`max_tokens` 96, temperature 0). It waits until the count of release lines holds for 4 s. Then it runs the reader while the child runs.
4. The reader again after the child exit.

Commands: `neg/run-k2.sh 10 1 2` (run 1, <time>) and `neg/run-k2.sh 12 1 2` (run 2, <time>).

## What the results show

- The chunks that the child released held KV data: 698,828,804 of 732,712,960 bytes were nonzero, and each full chunk gave 1,040 high-entropy samples. The test had real data to find.
- The scan path finds released, uncleared bytes when a process gets them back: the heap control found all its samples. A scan that turns a read error into "0 hits" would fail this control (fail-loudly-not-silently).
- Each fresh private buffer, shared buffer and CPU page that a new allocation got was all zeros. This held in the same process (plain private and shared controls), across processes from an ordinary process (`plant`), and from the sealed test child. The only path that gave old bytes back was a sub-allocation inside a heap that the same process still held.
- The child's own fresh chunks were all zero too. So the system gave zero-filled memory to every new allocation the reader made (16.1 GB). This does not show that the reader received the pages the child freed; physical page identity is not visible to a user process. (Wording narrowed 2026-10-24 after audit R2-10.)
- Each PASS line was graded by its control, not by the absence of hits (judge-the-method-not-the-claim). The criteria name what would falsify the claim, and the run tried to make that happen (falsification-beats-confirmation).

## Limits

1. The reader cannot see physical page numbers. "0 hits" means that the pages it got were zero. It does not prove that it got the child's pages. Every page in 16.1 GB was zero, so a non-zeroed reuse path would have to skip all of them. The test cannot exclude a reuse path that only a different allocation size, a different memory class (for example IOSurface or wired kernel memory) or a later time would reach.
2. The reader is a user process (uid 501, no sandbox). Root reads of GPU memory (P6, audit C5-04) are not tested here.
3. The test covers the release at the control pass while the child runs, and one scan after the child exit. The exit scan used the samples from the runtime releases only. Chunks that the child kept to the end (the prefix window) were not sampled.
4. The result holds for macOS `27.2-beta` on `Mac17,7`. Zero-fill is an OS and driver property, so a different OS build needs a new run.
5. Do not read "the system zero-fills new allocations" as "freed memory is cleared at once". The freed pages can hold the data until they are reused. Root or kernel access to physical memory is outside this test (misleading-with-truth).
