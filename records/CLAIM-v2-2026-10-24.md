## Claim

On a Mac in Full Security, with the macOS kernel, GPU driver and sandbox not damaged:

1. **Prompt content.** Root cannot read the content of the prompt from the memory of the engine or the child.
2. **Reply content.** Root cannot read the content of the reply from the memory of the engine or the child, or from the connection to the consumer.
3. **Model integrity.** Root cannot change the model without a change to the model hash that the consumer checks.
4. **No surface.** The child cannot open `IOSurfaceRootUserClient`, and the public Metal share APIs return nothing under the child's sandbox.
5. **Identity.** The engine that answers is the binary whose CD hash the consumer pins. The consumer checks that CD hash on each assertion.

The claim covers **content**, with one measured limit: root can read the speculative-step pattern of a reply, and that pattern carries information about the content (at temperature 0 it lets root check a guessed prompt; see Limits). It does not cover **length** or **timing**.

## Limits

**Length and timing (stated limit, not a defect):**

The length and timing numbers below were measured on the earlier build (engine `<h21>`, child `<h23>`); the speculative-step numbers on the current build. The engine and child code paths that make those frames did not change between the two builds.

- **Prompt token count.** The engine and the child exchange frames on a local `socketpair`. The request frame is 24 + 64 + 4 × (prompt tokens) bytes. Root reads those byte counts with `fs_usage`, which works with SIP on. Measured 2026-10-24 (`review/LENGTH-ROOT-2026-10-24.md`): request frames of 172 and 232 bytes gave 21 and 36 prompt tokens, equal to the tokenizer count.
- **Reply token count.** Each reply frame from the child is 24 + 16 + 4 × (tokens) bytes, so root reads the reply token count, including the end token (measured: 2 = 1 + end, and 24 = 23 + end).
- **Timing.** Root sees the time of each reply frame, so it sees the decode rate (about 49 ms between frames in the measured run) and the prefill time, which grows with the prompt (339 ms and 455 ms for the two measured prompts). The engine sends the network reply after generation ends, so the total reply time also grows with the reply length.
- **Shared prefix cache (open gap, not fixed).** The child keeps one prefix cache for all consumers. A request whose prefix (up to 8,192 tokens) another consumer sent a short time before gets its first token much faster (stored measurement: 15.5 s against 3.2 s). Any consumer can see this time, so one consumer can test whether another sent a guessed prefix. Root is not needed. Two sessions were not measured. Fixes and the test are in `review/PREFIX-CACHE-GAP-2026-10-25.md` (audit R5-4-01).
- **Speculative-step pattern (measured limit, not fixed).** Each reply frame is one decoding step. Its token count is the number of retained draft rows plus, at the end, one stop token or last budgeted token: 1 to 9 tokens (`ExecutionLimits::maximumStepTokens` in `model/Model.hpp`, `emitTerminalAnchor` in `model/Runtime.mm`). Root reads that count for each step, and the number of steps. Measured 2026-10-25 (`review/SPEC-TEMP-2026-10-25.md`, 4 open-ended prompts, 3 runs each, current build): at temperature 0 every prompt gave the same sequence in all 3 runs, and the 4 prompts gave 4 different sequences. So root can check a guessed prompt by running it on the same open models and comparing the sequence. `sealed-chat` sends temperature 0; the engine default is 0.6. At temperature 0.6 the sequences did not repeat, but the mean tokens per frame still separated kinds of text (2.35 to 5.52, margin 0.84). The network does not see the pattern. A fix would have to send a fixed number of tokens per frame at fixed times (for example, all frames at the end of generation, or a constant frame rate); padding each frame alone hides the count per step but not the number of steps. No fix is built. This is an open gap (operator decision 2026-10-25); the three possible fixes and their costs are in `review/SPEC-TEMP-2026-10-25.md`, section "Gap". Not measured: whether a second Mac gives the same sequence for the same prompt.
- **Network.** The padding (every reply frame is 1043 bytes of ciphertext; the frame count is rounded up to a power of two) hides the reply byte size from the network, not the reply timing. The sealed request is not padded: its ciphertext is 16 bytes longer than the plaintext, so the network sees the prompt byte length.
- **Status codes.** The HTTP status (500, 503, 422) shows which provider limit a request hit. A 503 shows that the child refused the request or stopped during generation (the KV budget, capacity, or a retryable child error). That is one bit about the size of the prompt plus the reply so far. Neither the reply nor the engine log carries the token count.

**Platform:**

- Apple Silicon gives no memory encryption to third-party code. A kernel or GPU-driver defect breaks the claim.
- **Boot posture and host settings.** No field in the Apple attestation certificate names the boot policy (`Full Security` vs `Reduced`/`Permissive`), SIP, swap encryption, or the sleep setting. Three layers cover this instead:
  1. **Pinned engine gate (`sealed_posture.c`, closed on the pinned binary).** At start (before the package or the child is opened), the engine requires `csr_get_active_config == 0`, empty `kern.bootargs`, `vm.swapusage.xsu_encrypted == 1`, `kern.hibernatemode` in `{0, 3}` (refuses `25`), 0 non-Apple kexts (`KextManagerCopyLoadedKextInfo`), and `IODeviceTree:/chosen` properties `effective-security-mode-ap == 1`, `certificate-security-mode == 1`, `effective-security-mode-sep == 1`. Before `/attest`, `/session`, `/probe` or `/infer`, the engine re-checks SIP, swap encryption and `kern.hibernatemode` inside its R8 sandbox (`boot-posture`, `boot-posture-unit`, mutant `BAD_CSR`). A provider who edits the engine binary to skip this check gets a different CD hash, which the consumer refuses.
  2. **Consumer macOS floor (`MinOSVersion = 27.0`, closed).** The consumer checks the attested macOS version (`1.2.840.<time>.100.8.7` tag `1400`) against a floor of `27.0` by default (`--min-os` / `SEALED_MIN_OS`; `refuse-old-macos`).
  3. **Apple App Attest server behavior on weakened boots (measured on one M1, not an Apple specification).** In our 2026-09-26 tests on an M1 (macOS 27.0), App Attest refused to issue a certificate for a new key in 4 of 4 weakened boots (`csrutil disable` twice, partial SIP, and `Reduced Security`, each returning `Unexpected ACM requirement: 23`; `Full Security` succeeded 7 of 7), and keys stopped working across every restart (2 of 2). That behavior is not documented by Apple and has not been re-run across the 12-cell recoveryOS grid (`A-11`) on the M5. If Apple's server ever issued an attestation in a weakened boot and a kernel/SIP bypass let root patch the running engine in memory without changing its on-disk executable pages, the consumer could not detect it from the attestation alone.
- **Not tested:** root substitution of the Metal compiler service (P8). Its only test is R4-T5, and the R4-T5 control did not fire, so the two R4-T5 EXEMPT arms are not evidence for P8. Panic dumps (P5e) are not measured.
- Four root-kit arms are EXEMPT: A-2 dtrace read (SIP blocks the provider), R4-T5 pid domain and control (launchd refuses), and A-4 Endpoint Security (AMFI kills the kit client at launch, exit 137, because no provisioning profile permits its endpoint-security entitlement; an Apple-signed client such as `eslogger` was not measured).
- N3: bytes present when R2 checks the frame are refused; bytes that arrive later are not.
