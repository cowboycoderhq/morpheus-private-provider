# A-11 reduced cell on macOS 26B131 (2026-11-17)

Host: this M5, `Mac17,7`, macOS 27.2.1 `26B131`, SIP fully on, Developer Mode on.
Kit: `build-glm/wave-2026-10-06/kits/a11-grid`, grid `grid-2026-11-17`.
Adversarial passes 1-5 in `scratch/A11-ADVERSARIAL-*.md`.

## Question

The engine gate reads SIP config, boot arguments, swap, hibernatemode, kexts,
and the chosen device-tree mode. In a Reduced boot with SIP fully on, every one
of those reads is identical to Full, so the gate cannot tell Reduced from Full.
Does Apple's App Attest layer refuse a key in that boot?

## Cells

| Cell | Boot mode | SIP | Fresh attestation | Assertion |
|---|---|---|---|---|
| `full-sipon-devmode-on` | Full | on | `OK` | `OK` |
| `reduced-sipon-devmode-on` | Reduced (smb0=1) | on | `DCErrorInvalidKey` (error 3) | not reached |
| `stalekey-full-in-reduced` | Reduced | on | — | `DCErrorUnknownSystemFailure` (error 0) with the Full-cell key after two starts |

The `bputil` output for each cell is in its folder. `csrutil status` read
`enabled.` in all cells. The engine posture line was identical in the Full and
Reduced cells (`rc=0 csr=0x0 bootargs= swap_enc=1 hibernate=0 non_apple_kexts=0
ap=1 cert=1 sep=1`), which is the gate's blind spot made visible.

## Call split (post pass 5)

The probe was patched to write `keygen.txt` immediately after `generateKey`,
before `attestKey`, then re-signed (new CD hash). The run was in the SAME
Reduced boot as the `reduced-sipon-devmode-on` cell: boot time `<date> <time>`
in both records, 19 minutes after the cell, no start between. The boot's
`csrutil`, `bputil`, and engine-posture lines are the cell folder's.

- `keygen.txt` written, 44 bytes → `generateKey()` succeeded.
- `attest.json` → `DCErrorInvalidKey` (error 3) → `attestKey()` failed.

So the failure is in the attestation round trip, not in key generation.
Two error-3 observations, both in one Reduced boot: the first with the
original binary (the same binary as the Full control), the second with the
patched binary. The error is not an artifact of the re-sign. Two runs in one
boot do not address the paired-repetition hole.
Artifacts: `grid-2026-11-17/results/keygen-split-in-reduced/`.

## Stale key (post pass 1) and its Full-boot control (post pass 8)

The key minted in the Full cell (`keyId.txt`) was used in the Reduced boot
after two starts: `DCErrorUnknownSystemFailure` (error 0). The Full-boot
control, run in the restored Full boot after three starts with the same key,
returned the same error 0 (`grid-2026-11-17/results/stalekey-full-in-full/`). So on the stale-key
path the starts, not the boot mode, are the cause: the assertion fails after
restarts in both measured boot modes (two starts into Reduced, three into
Full). Whether the key is invalid, inaccessible, or desynced by counter is
unmeasured. This matches the M1 slice, 2 of 2
(the attest-slice record of 2026-09-26, U2 row). The
attack "mint in Full, start into Reduced, serve" is closed on the measured
paths, if the post-restart failure is not an artifact of the harness; the
error-0 mechanism is unmeasured.

## Probe key flow, recorded from source

`attest` mode: `generateKey()`, then write `keygen.txt` (added 2026-11-17;
before that, the id was written only after `attestKey` succeeded), then
`attestKey(keyId, clientDataHash:)`, then write `keyId.txt`. `assert` mode:
read `keyId.txt`, then `generateAssertion(keyId, clientDataHash:)`. So the
error-3 key was created and attested inside one Reduced boot. The fresh-key
result carries no restart confound.

## Verdict for the claim

On this machine and build, in one paired run, a provider in a Reduced boot has
no usable App Attest identity on either measured path. In the Reduced boot,
`generateKey` succeeds and `attestKey` returns `DCErrorInvalidKey`; the call
split was a later run in the same boot, not part of the paired run. The split
was measured only in that second run, with the re-signed probe. The first
observation's failing step is inferred from the shared error code, not
measured. Two runs in one boot, 19 minutes apart, weaken a one-off transient
as the cause; they are not repetition. The
mechanism (server or local ACM) stays open, though the header's three
documented triggers for error 3 leave the service-rejection trigger as the one
that fits: the key was fresh, the failing call was `attestKey`, and
`DCErrorServerUnavailable` was not returned. Permissive with SIP on was not
measured.

## One-start mechanism (2026-11-17, post pass 10)

A fresh key was minted and attested in a Full boot (<time> UTC), the Mac was
started once, and the assert ran in the next Full boot, logged in, through
LaunchServices. Result: error 0 again. The captured `devicecheckd` log
(`grid-2026-11-17/results/one-start-full/devicecheckd-log.txt`) shows the chain:

1. The key is retrieved from the SEP: `SEPClientObject: getKey` succeeds, and
   the public bytes are extracted (`SecKeyCopyExternalRepresentation`).
2. The CD-hash extensions are appended, so the attestation context is intact.
3. `SecKeyCreateSignature` is called on the SEP.
4. The SEP refuses: `<sepk:p256(s) kid=<h110>>: unable to sign
   digest`, `AKSError=-536362989`.

So the post-start failure is not an inaccessible key and not a harness
artifact: the SEP holds the key and refuses to sign with a key minted in a
different boot. The error matches the M1 slice exactly (2 of 2,
`AKSError -536362989`). The attack "mint in Full, start into another boot,
serve" is closed at the hardware level. The assert path made no network call,
which is expected: `generateAssertion` is local.

## Permissive cell and the error-3 mechanism (2026-11-17, later)

The Permissive cell ran after the `csrutil enable` rule was found (that command
resets the boot mode to Full, so the kit now forbids it after a `bputil` mode
change):

- Boot mode verified `Permissive (smb0 && smb1): 1`, SIP `enabled.`
- Engine gate: `rc=0`, posture identical to Full (the gate's second blind mode).
- Fresh attestation: `DCErrorInvalidKey` (error 3), the same refusal as the
  Reduced cell.

### Where the error-3 refusal happens

A debug-level `log stream` on `devicecheckd` ran during a failing attest in the
Permissive boot (`grid-2026-11-17/results/err3-mechanism-permissive/`). The
sequence, <time> to .062 (13 ms):

1. `SecKeyCreateRandomKey` / `SEPClientObject: createKey` — key generation
   succeeds in the SEP.
2. The attest path evaluates an access control through LocalAuthentication:
   `SecAccessControlRef: f;osgn(csec(pslvl(1)));odel(true);oa(true);ok(true)`.
3. The evaluation fails. devicecheckd loads the strings `Authentication
   canceled.` and `Authentication failure.`
4. The app receives `DCErrorInvalidKey`.

No network marker appears in the ~1000 captured lines: no `apsd`, no
`NSURLSession`, no `albert`, no server host. The only `apple.com` text is a
plist DTD in an `lsd` line. The failure precedes any server contact, and the
13 ms window is too short for a round trip. So the refusal is local: an SEP
access-control requirement (`csec(pslvl(1))`) that the weakened boot does not
satisfy. This matches the M1 slice's `Unexpected ACM requirement: 23`.

Caveats: `log stream` reports dropped messages, so the capture is not
complete; `pslvl(1)` is undocumented and recorded verbatim; the capture ran in
the Permissive boot, and the Reduced cell's identical error code is inferred
to share the path.

## Grid outcome (2026-11-17, closed)

The final grade over three cells prints `FAIL grid`. The failing row is the
pre-registered gate rule for Permissive:

```
FAIL permissive-sipon-devmode-on engine-posture - gate SERVED a weakened boot rc=0
```

The interpretation, fixed before the run: a Permissive cell that the gate
serves shows the gate cannot see that mode. The data confirms it, and the same
holds for Reduced: every read the gate has (`csr` config, bootargs, swap,
hibernatemode, kexts, the chosen device-tree mode `1,1,1`) is identical across
Full, Reduced, and Permissive-with-SIP-on. No user-readable discriminator was
found in any cell. `bputil -d` needs root, and the engine does not run as root.

The load-bearing rows all passed: App Attest refused a new key in the Reduced
and in the Permissive boot, and the Full controls attested and asserted in
every Full boot. So the FAIL row is a finding about the gate, not about the
claim: the public sentence already says the gate cannot distinguish Reduced or
Permissive from Full, and the protection for both modes is the SEP's local
access-control check. The grading criterion assumed a readable discriminator
exists for Permissive; the run falsified that assumption. The criterion stands
as written and the FAIL is recorded.
